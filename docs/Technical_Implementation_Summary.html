1. Overview

Purpose. Receive Stripe checkout.session.completed webhooks, confirm that each one was really sent by Stripe, extract the payment details and forward a short, normalized notification to a configurable internal notification API.

Event flow.

Stripe --POST /webhooks/stripe (Stripe-Signature)--> webhook service
   1. verify signature on the raw request bytes
   2. keep only checkout.session.completed with a successful payment
   3. skip events already forwarded
   4. map session fields to the notification payload
   5. POST to INTERNAL_API_URL with a Bearer token and a timeout
   6. answer Stripe: 2xx = done, non-2xx = please redeliver
ItemDetail
RuntimeNode.js 20 or newer, ES modules. Developed and tested on Node.js 24.17.0.
Dependenciesexpress 4 (HTTP), stripe 17 (signature verification), dotenv 16 (loads .env). No others; outbound HTTP uses Node's built-in fetch.
TestsNode's built-in test runner (npm test), no extra packages.

2. Architecture

ModuleResponsibility
src/server.jsEntry point. Loads and validates configuration, starts the service and (optionally) the local receiver.
src/app.jsExpress app. The webhook route uses express.raw({ type: 'application/json' }) so the handler gets the unmodified bytes; the JSON parser is registered after it.
src/webhook.jsThe handler: signature verification, event filtering, idempotency check, mapping, forwarding, HTTP response and audit log.
src/checkout-session.jsField mapping and the rule for "payment successful".
src/notification-client.jsAuthenticated POST with timeout. Turns every failure into one of three categories: timeout, network, http_error.
src/idempotency-store.jsRemembers forwarded event ids (in memory, 24 h, max 10,000).
src/config.js, src/logger.jsEnvironment configuration with validation; JSON-lines audit logger with email masking.

Signature verification

stripe.webhooks.constructEvent(rawBody, signatureHeader, STRIPE_WEBHOOK_SECRET) is called with the raw Buffer and the Stripe-Signature header. It recomputes the HMAC-SHA256 signature and also rejects timestamps older than five minutes (replay protection). A missing header or a failed check returns HTTP 400 before any payload is read or forwarded.

Event filtering

Only checkout.session.completed is processed. Other verified event types get 200 and are ignored. A completed session whose payment_status is neither paid nor no_payment_required (delayed payment methods) is also acknowledged and not announced, because the money has not arrived yet.

Field mapping

Checkout Session fieldNotification fieldRule
idtransaction_idrequired string
customer_details.emailcustomer_emailnull when Stripe has no email
amount_totalamountrequired integer, minor units (4999 = 49.99)
currencycurrencyrequired, lowercase ISO 4217
payment_statusstatusrequired string

If a required field is absent the service answers 422 and names the field. The output for the supplied fixture equals fixtures/notification-payload.expected.json exactly (checked by a test).

Downstream API call

POST INTERNAL_API_URL with Content-Type: application/json, Authorization: Bearer INTERNAL_API_TOKEN and Idempotency-Key: <Stripe event id>. Any 2xx answer counts as delivered (the supplied receiver answers 202).

3. Configuration

All settings are environment variables, loaded from a git-ignored .env file in development. .env.example contains placeholders only.

VariableRequiredMeaning
STRIPE_WEBHOOK_SECRETyesEndpoint signing secret from stripe listen or the Stripe dashboard
INTERNAL_API_URLyesNotification endpoint; default points at the local receiver
INTERNAL_API_TOKENyesBearer token for the notification endpoint
INTERNAL_API_TIMEOUT_MSnoForwarding timeout, default 5000
PORTnoWebhook service port, default 4242
STRIPE_SECRET_KEYnoStripe test key; not needed to verify signatures
START_MOCK_NOTIFICATION_API, MOCK_API_PORTnoSwitch off or move the bundled local receiver

The service exits at start-up with a clear message if a required variable is missing or the URL is not valid. The message lists variable names only.

Stripe CLI commands.

stripe login
stripe listen --forward-to localhost:4242/webhooks/stripe
stripe trigger checkout.session.completed

The whsec_... value printed by stripe listen goes into STRIPE_WEBHOOK_SECRET. To use a real internal messaging service, change INTERNAL_API_URL and INTERNAL_API_TOKEN and set START_MOCK_NOTIFICATION_API=false; no code change is needed.

4. Reliability and security

SituationResponseBehaviour
Forwarded / duplicate / ignored200Stripe stops delivering the event
Signature missing or invalid400Nothing processed or forwarded
Required field missing422Field name logged and returned
Receiver unreachable or non-2xx502Logged as network or http_error; Stripe redelivers
Receiver timed out504Request aborted with AbortSignal.timeout; logged as timeout; Stripe redelivers
  • Timeout. One bounded attempt per delivery (default 5 s), so the service always answers Stripe promptly.
  • Retry. The service does not retry by itself. A non-2xx answer makes Stripe redeliver with exponential backoff (up to three days in live mode). This is durable across restarts of this service, which an in-process retry loop would not be.
  • Idempotency. An event id is stored only after the receiver accepted the notification. A repeat of a delivered event gets 200 "duplicate" and is not forwarded again; a repeat of a failed event is forwarded. The event id is also sent as Idempotency-Key so the receiver can de-duplicate.
  • Structured logs. One JSON object per line with timestamp, level, event, event_id, event_type, stage, error_category and http_status.
  • Sensitive data. Secrets, the signature header and request bodies are never logged. Customer emails are masked (a***@example.test). Error responses to the caller are generic. .env is excluded by .gitignore; the Postman files contain placeholders only.

6. Deployment

Source. https://github.com/vicky-masai/stripe-checkout-webhook-bridge

To run. npm install, create .env from .env.example, npm start. For a hosted deployment set the same variables in the platform's secret store, expose POST /webhooks/stripe over HTTPS, register that URL in the Stripe dashboard for checkout.session.completed and use that endpoint's signing secret.

Limitations.

  • Verified in Stripe test mode only; not exercised with a live-mode account or a deployed HTTPS endpoint.
  • Duplicate detection is in memory: per instance and cleared on restart. With several instances, use a shared store (for example Redis) or rely on the receiver honouring Idempotency-Key.
  • Payments completed later through delayed payment methods arrive as checkout.session.async_payment_succeeded, which is outside the assignment scope and is ignored.
  • The bundled receiver is a local test stand-in, not a real messaging service. Connect a real one only with its owner's authorisation and credentials.
